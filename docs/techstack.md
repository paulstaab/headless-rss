# Rust Reimplementation Tech Stack Plan

## Goals
- Reimplement `headless-rss` in Rust while preserving API compatibility (service endpoints plus Nextcloud News `v1-2` and `v1-3`).
- Keep compatibility with the existing SQLite database so existing `data/headless-rss.sqlite3` files are usable.
- Preserve current operational model: self-hosted, single-container deployment, background periodic feed updates, and CLI support.

## Proposed Stack

### Runtime and Language
- Rust stable toolchain (`rustup`, `cargo`, `rustc`).
- Edition: Rust 2024 (or latest stable at implementation start).

### HTTP API
- `axum` for API routing and handlers.
- `tower` / `tower-http` for middleware (auth, tracing, compression, CORS if needed).
- `serde` + `serde_json` for request/response contracts using camelCase fields.

Why: small, async-native stack with good ecosystem support and simple composition.

### Async Runtime and Scheduling
- `tokio` runtime.
- `tokio::time::interval` for periodic feed updates.
- `tokio::spawn` for startup-triggered and periodic update tasks.

Why: first-class async ecosystem and robust scheduling primitives.

### Database Layer (SQLite Compatibility)
- `sqlx` with SQLite driver.
- Migrations via `sqlx migrate` with SQL files mirroring current schema and constraints.
- `chrono` or `time` crate for timestamp handling.

Compatibility approach:
- Keep table names, column names, nullability, defaults, and unique constraints compatible with current DB.
- Use the same SQLite file path (`data/headless-rss.sqlite3`) by default.
- Validate compatibility against a copy of an existing Python-generated DB.

Note: we can also evaluate `rusqlite` for tighter low-level control, but `sqlx` gives async support and better compile-time query checks.

### Feed Fetching and Parsing
- `reqwest` for HTTP fetching.
- `feed-rs` for Atom/RSS parsing.
- `scraper` for HTML extraction and thumbnail heuristics.
- Optional: `readability-rs` (or custom extraction logic) for full-text extraction.

### Email / IMAP
- `imap` (sync) or `async-imap` (async) for mailbox integration.
- `native-tls` / `rustls` depending on deployment preferences.
- `mailparse` for parsing MIME emails.

### Auth and Security
- HTTP Basic auth middleware in `axum`.
- URL validation/SSRF protections using:
  - `url` crate for URL parsing.
  - `trust-dns-resolver` or system DNS + explicit IP filtering for private/link-local/loopback blocking.

### CLI
- `clap` for command-line interface parity:
  - `update`
  - `add-email-credentials`

### Observability
- `tracing` + `tracing-subscriber` for structured logs.
- Optional JSON logging mode for containerized deployments.

### Testing
- `cargo test` unit/integration tests.
- API tests via `axum` test server + `reqwest`.
- SQLite compatibility tests using real fixture DB files generated by current Python implementation.

### Packaging and Dev Experience
- Multi-stage Docker build (builder + slim runtime).
- Buildx GitHub Actions cache (`cache-from/cache-to type=gha`) for faster repeated multi-arch (`amd64`/`arm64`) builds.
- Continue devcontainer-based local development with Python tooling plus Rust/Cargo support during migration.

## Compatibility Strategy
- Phase 1: Create Rust schema model and verify reads against current SQLite file.
- Phase 2: Implement read-only API endpoints (`status`, folder/feed/item list/version) and compare payloads.
- Phase 3: Implement write operations and background update workflows.
- Phase 4: CLI parity and migration validation.
- Phase 5: side-by-side verification against Python implementation.

## Confirmed Decisions (2026-03-05)
- Web framework: `axum`.
- Database library: `sqlx` with SQLite.
- First milestone scope includes:
  - Core API parity (`status`, feeds, folders, items).
  - CLI parity (`update`, `add-email-credentials`).
  - Background scheduler/feed update loop.
- Schema compatibility target: latest schema only (database should be migrated to head first).
- API implementation order: implement `v1-2` and `v1-3` in lockstep.
- Migration source of truth: Rust-first SQL migrations.
- OpenAI summarization: implement after core parity.
- IMAP/newsletter ingestion: implement after core parity.
- Runtime model: single process with embedded scheduler.
- TLS preference: no strict preference recorded.
- Transition strategy: no explicit dual-run deliverable required.

## Initial Recommendation
- Start with `axum + tokio + sqlx + reqwest + feed-rs + clap + tracing`.
- Target latest schema compatibility first (after migrations).
- Prioritize API parity and DB compatibility before optional features (LLM and advanced newsletter processing).
- Use Rust-managed SQL migrations as canonical once Rust implementation begins.
